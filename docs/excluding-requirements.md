# Excluding Python requirements

Sometimes an upstream service lists a runtime dependency in its
`requirements.txt` that we do not want in our images -- typically because it
is unused in our deployments and drags in a heavy transitive tree that has to
be compiled from source under `PIP_NO_BINARY=:all:`. This guide describes how
to drop such a dependency (and its exclusive transitive subtree) from the
generated lockfiles.

This mirrors the RDO distgit specs, which strip the same packages from
`requirements.txt` during `%prep` (e.g. the ceilometer spec drops `awscurl`).

## When to use this

Use an exclusion when **the dependency exists only because of a top-level
requirement you do not want**. You remove the *parent* package; `pip-compile`
then re-resolves and any transitive dependency whose *only* remaining parent
was that package disappears automatically. A transitive dependency that still
has another live parent is correctly kept.

This is the right (and only) lever for removing packages from the dependency
set, because the package set is derived from source at lock-generation time.
It is **not** for:

- **Pinning or bumping versions** -- that is what the normal
  `update-sources` / `update-lockfiles` flow does.
- **Packages provided another way at runtime** (e.g. from an RPM) -- those are
  handled by the `rpms.in.yaml` / RPM lockfile mechanism.
- **Removing a transitive dependency whose parent you want to keep** -- you
  cannot safely do this; deleting a genuinely-needed dependency just yields a
  runtime `ImportError`. Fix it upstream (loosen the parent) or stop using the
  parent.

## How it works

Exclusions live in `containers/<project>/excluded-requirements.txt`, one
package name per line. Each listed package is `sed`-deleted from a source
tree's `requirements.txt`. This strip happens in **two** places against the
same list:

1. **During `update-sources`** (on the host): `build.sh` clones the upstream
   source and runs its `apply_requirement_exclusions` step *before*
   `pip-compile` runs, so the excluded package and its exclusive subtree never
   enter `requirements.lock.<stream>` or `buildrequirements.lock.<stream>`.
2. **In the Containerfile build stage** (inside `buildah`): the service's
   Containerfile copies its `excluded-requirements.txt` into the build and runs
   the same `sed` over its own copy of the sources *before* the service wheel is
   built, so the excluded package is dropped from the wheel's own metadata too.

The second step is what makes a plain `buildah build` from pre-populated
`src/` directories (with no `update-sources` preparation) produce the same
dependency set as the lockfile-driven flow: without it the service wheel would
still declare the excluded package in its `Requires-Dist` and pull it back in
at install time. Both strips use the same `sed` pattern and are idempotent.

Matching is case-insensitive, anchored to the start of the line, and requires
the package name to be followed by a version specifier, extra, marker,
whitespace, comment, or end-of-line -- so listing `foo` will not accidentally
remove `foo-bar`.

**Important:** the *lockfile* is only re-resolved on the `update-sources` path,
which re-clones source and re-runs `pip-compile`. `update-lockfiles` feeds the
existing flat lockfile back into `pip-compile` (every transitive dependency is
already an explicit line, with no parentage left to prune), so it can neither
apply a new exclusion nor re-introduce one that has already been compiled out.
Always flush a new exclusion into the lockfiles with `update-sources`.

## What changes

Adding an exclusion to an **already-enabled** project touches three files, only
the first edited by hand:

| File | Edited how |
|------|------------|
| `containers/<project>/excluded-requirements.txt` | **By hand** -- add the package name |
| `containers/<project>/requirements.lock.<stream>` | Regenerated by `update-sources` |
| `containers/<project>/buildrequirements.lock.<stream>` | Regenerated by `update-sources` |

Once a project's Containerfile carries the strip block (see below), it does
**not** change when you add or remove an individual exclusion -- the block
reads the package names from `excluded-requirements.txt` generically, so editing
that file is all that is required.

### Enabling exclusions for a service

The Containerfile-side strip is not universal; it is added only to services that
ship an `excluded-requirements.txt` (e.g. the telemetry images -- aodh,
ceilometer, cloudkitty -- which drop `awscurl`). Add the block below to the
service's **build** stage, after the sources are copied (`COPY .../src/ /src/`)
and *before* the service wheel is built. For example, in a ceilometer
Containerfile:

```dockerfile
# Drop excluded upstream requirements before building the service wheel, so the
# wheel's own metadata (Requires-Dist) cannot pull them back in at install time.
# Mirrors the RDO ceilometer distgit spec, which strips the same packages from
# requirements.txt in %prep. See docs/excluding-requirements.md.
COPY excluded-requirements.txt /tmp/excluded-requirements.txt
# Pre-strip comments, inline whitespace, and blank lines inline so the loop sees
# one bare package name per line -- identical to the host-side strip in build.sh.
RUN sed -e 's/#.*//' -e 's/[[:space:]]//g' -e '/^$/d' /tmp/excluded-requirements.txt | \
    while IFS= read -r pkg; do \
      for req in /src/*/requirements.txt /src/overrides/*/requirements.txt; do \
        if [ -f "${req}" ]; then \
          sed -i -E "/^${pkg}([[:space:]<>=!~;,#[]|\$)/Id" "${req}"; \
        fi; \
      done; \
    done && \
    rm /tmp/excluded-requirements.txt
```

The `COPY` names `excluded-requirements.txt` directly, and the `RUN` does no
existence check, because `buildah` fails the `COPY` outright if the file is
missing. That is deliberate: the block is added only to services that actually
have an exclusion file. Comments and blank lines are stripped up front so the
loop iterates over bare package names only, and the line-deleting `sed` pattern
is identical to the host-side one in `build.sh`, so both paths strip exactly the
same lines.

## Workflow

1. **Edit the exclusion list.** Create
   `containers/<project>/excluded-requirements.txt` if it does not exist, and
   add the package name. Include a comment explaining *why* -- this file is the
   only record of the exclusion's intent:

   ```
   # awscurl is not used in our deployments and pulls a heavy transitive tree
   # (awscrt, boto3, s3transfer, configargparse) that must otherwise be
   # compiled from source under PIP_NO_BINARY=:all:. The distgit drops it too.
   awscurl
   ```

2. **Regenerate the locks from source**, at current pins so the only diff is
   the removal (not a mass re-pin):

   ```bash
   SKIP_HASH_UPDATE=1 STREAM=master ./build.sh update-sources <project>
   ```

   `SKIP_HASH_UPDATE=1` keeps the existing pinned source hashes; drop it only
   when you also intend to move to the latest upstream. This single command
   re-clones, strips the excluded requirements, and regenerates
   `rpms.in.yaml`, `requirements.lock.<stream>`, and
   `buildrequirements.lock.<stream>`.

3. **Verify** the excluded tree is gone and shared transitives are kept:

   ```bash
   # excluded parent and its build-only deps gone:
   grep -iE '^(awscurl|configargparse)' containers/<project>/requirements.lock.master
   grep -ic configargparse containers/<project>/buildrequirements.lock.master   # -> 0

   # a transitive with another live parent is still present:
   grep -iE '^botocore' containers/<project>/requirements.lock.master
   ```

4. **Commit all three files together** (`excluded-requirements.txt` plus both
   regenerated `*.lock.<stream>` files) so the intent and its compiled result
   stay in sync.

## Durability

The excluded package is not deleted from upstream -- it is stripped on *every*
`update-sources` run. It therefore stays out only as long as its line remains
in `excluded-requirements.txt`. Remove the line and re-run `update-sources`
and the whole subtree returns. `update-lockfiles` never re-introduces it,
since it only re-pins the already-clean set.
